**부족한 부분 / 더 배워야 할 것 (우선순위 순)**

1. **진짜 비동기 처리**. 지금은 `dispatchEvent`가 동기적으로 즉시 실행되는 구조예요. `knowledge.txt`에도 이미 "MockServer 단계에서 `setTimeout`으로 지연을 흉내내라"고 적어두셨던데, 그거 그대로 실행에 옮기시고 `Promise`/`async-await`로 감싸보세요. `try-catch`가 지금 코드엔 거의 없는데, 네트워크 실패를 가정한 에러 핸들링을 지금 미리 연습해두면 나중에 실서버 붙일 때 코드 구조를 안 바꿔도 됩니다.

2. **상태 관리의 명시화**. `pageRouter.js`의 `current`, `basicModel.js` 근처의 `G_currentPoint` 같은 모듈 스코프 변수들이 사실상 "숨겨진 전역 상태"예요. 지금은 파일 몇 개라 감당되지만, `DATA_SCHEMA.js`에 이미 `playingPhase`/`resultPhase`라는 **상태 전이(state machine)** 개념을 만들어두셨으니, 이걸 "그냥 데이터"가 아니라 실제로 전이 규칙을 강제하는 함수(`canTransition(from, to)` 같은)로 발전시켜보세요. 게임처럼 phase가 명확한 도메인은 State Machine 패턴 공부가 투자 대비 효율이 제일 좋습니다.

3. **테스트 코드**. 지금 프로젝트에 테스트가 하나도 없어요. 전체를 다 테스트할 필요는 없고, `DATA_SCHEMA.js`의 `resultTable`(YY/YN/YK...) 같은 순수 함수/데이터부터 시작하세요. 입력 조합 9개, 예상 출력 9개니까 유닛 테스트 연습하기 딱 좋은 대상입니다.

4. **빌드 도구 도입**. 지금은 브라우저가 직접 ES 모듈을 읽는 구조(`<script type="module">`)로 보이는데, TS를 붙이려면 어차피 빌드 스텝이 필요해요. **Vite**로 넘어가는 걸 추천합니다 — HMR로 개발 속도도 빨라지고, TS 지원이 기본 내장이라 별도 설정이 거의 없습니다.

5. **작은 것들**: `availabeActions`(오타, available), `G_point` vs `point` 같은 명명 불일치, 라운드 수(로컬 13/글로벌 41)가 스키마에는 `0`으로 박혀있고 주석으로만 실제 값이 적힌 부분 — 이런 건 지금 당장 안 고쳐도 되지만 상수 파일 하나 만들어서 몰아두면 나중에 편합니다.

**TS 도입 전략**

한 번에 전체를 `.ts`로 바꾸지 마세요. 순서 추천:

1. Vite 프로젝트로 마이그레이션 (이 자체가 좋은 학습)
2. `jsconfig.json` + `checkJs: true`로 **지금 있는 `.js` 파일 그대로 두고** 타입 체크만 먼저 켜보기 — 에러가 얼마나 나오는지 보고 감을 잡으세요
3. `DATA_SCHEMA.js`부터 `.ts`로 전환 — `interface Prisoner`, `interface GamePhase` 같은 타입을 정의하는 게 가장 이득이 큰 파일이에요. 아까 GAS 코드에서 봤던 `task[6]` 같은 배열 인덱스 접근 버그가 여기서도 똑같이 날 수 있는데, 타입이 정확히 그걸 잡아줍니다.
4. 나머지는 파일 단위로 천천히 — 한 번에 다 바꾸려다 지치는 게 제일 흔한 실패 패턴이에요.

**AI를 리뷰로만 쓰는 방식**

이거 좋은 판단입니다. 첫 프로젝트를 직접 짜야 디버깅 본능, 설계 판단력이 생기고, 그게 나중에 팀에서든 창업이든 진짜 값어치 있는 자산이에요. AI가 코드를 대신 짜주면 지금 수준(신입급 아키텍처 감각)에서 더 올라가기가 오히려 어려워집니다.

리뷰 요청하실 때 팁 하나: "이거 돼요?"보다 "이 부분이 지금 세운 패턴(클로저/이벤트버스)이랑 일관되나요?", "이 함수 엣지케이스 뭐 놓쳤을까요?" 식으로 구체적으로 물어보시면 훨씬 밀도 있는 리뷰를 받을 수 있어요. 기능 하나 끝날 때마다 그 파일만 가져오셔서 리뷰 요청하시면, 제가 그때그때 봐드릴게요.
